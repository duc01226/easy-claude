# Running an experiment

Read when preparing, executing or recovering a campaign. Run from the consuming project root. The controller uses Node18+ built-ins and Git. Live execution defaults to an installed authenticated Codex or Claude Code CLI; Docker with a trusted pre-provisioned image is optional. A platform/CLI lane without observed execution remains NOT RUN.

## Native runtime preparation

Probe `node --version`, `git --version` and the chosen CLI's `--version` and login-status command (`codex login status` or `claude auth status`). Sign in through that CLI's normal account flow when needed. A successful status command is not proof that inference works; a model/login failure remains blocked or invalid evidence with its actual diagnostic. Claude's status command also reports a login whose stored access token has expired. Before preflight and each Claude model session, the runner checks the stored token outlives that session's timeout plus five minutes; if not, it runs one minimal prompt through the maintainer's own CLI in their normal environment so the CLI renews and stores the token itself, then re-reads it. The private profile only ever receives the access token. A token still too short after renewal blocks the session with ENVIRONMENT-BLOCKED; an exported `CLAUDE_CODE_OAUTH_TOKEN` (for example from `claude setup-token`) is used as given. Task tools and offline check dependencies must already be available through the consumer's supported setup. Preflight checks required CLI capabilities, not every task toolchain.

Omit `--runtime` to resolve an available authenticated CLI, its configured explicit model and installed version before sealing. Selection checks Codex first, then Claude; use `--host`, `--model` and `--judge-model` on `prepare` to choose explicitly. Mutable defaults and unresolved required identities are rejected rather than guessed. The assessor defaults to the resolved solver model. Discovery makes no inference request.

For explicit settings, a native runtime uses `schemaVersion: 1`, `backend: "host"`, `host: "codex"` or `"claude"`, the complete exact `cliVersion` output, explicit `model` and `judgeModel`, `repeats`, `seed`, `timeoutMs` and `maxTurns`. Automatic selection defaults to one pair, seed42, 30 minutes and 200 turns/actions; set a runtime file to change campaign limits. An omitted backend with no image selects host mode; an image-only runtime retains Docker selection. Container-only image/resource fields are rejected in native mode. Optional positive `budgetUsd`/`judgeBudgetUsd` are model-loop allowances only where the CLI supports them. Per arm, skilled assessment budgets one solver plus one observer and up to `assessment.maxPasses` quality sessions; legacy budgets two judge calls. These cannot cap subscription billing. Native mode has no hard CPU, memory or disk quota. Codex rejects dollar-loop limits and bounds completed command/file/tool actions under `maxTurns`; it does not report those as model-turn counts.

Native execution reuses only the selected login in a private temporary profile, excluding personal guidance, hooks, plugins, memory and prior conversations. Supported credential bridges are the Codex file login cache, and Claude's existing OAuth access token or credential store, including the macOS keychain. An unsupported store fails explicitly. Windows requires its built-in PowerShell ACL verification before private files are written; macOS/Linux enforce private directory permissions. No provider API key is required. Authentication files/private session homes are removed during cleanup and never retained as benchmark artifacts; do not put credentials in case/runtime files or reports.

Every native solve, check and review receives its own Git worktree from a fresh synthetic repository containing only frozen inputs, without original history/remotes/author identity. Raw and reviewer sessions suppress personal/ancestor guidance; raw Claude solvers and journey observers also pass `--disable-slash-commands`, because `--safe-mode` still lists the CLI's own built-in skills (preflight blocks a CLI without that flag), so raw sees no skill at all; framework solvers receive only their frozen installation and setup. Skilled outcome reviewers receive the same neutral frozen reviewer toolkit for both arms, excluding automatic hooks and solver setup. Native solving uses the CLI's normal sandbox/permissions. Claude sessions may bind loopback ports (`allowLocalBinding`) so server-style tasks can run real HTTP tests; every outbound domain stays blocked. Without it, binding fails with EPERM and solvers fall back to weaker in-process tests. Outcome assessment permits report/scratch writes and bounded checks, while verifying candidate/toolkit final bytes; journey observation and legacy review are read-only. Checks execute trusted candidate code on the host in fresh worktrees with no supplied provider login. Holdouts are withheld while solving. Worktrees separate source and context; they do not contain malicious code or make outside files inaccessible. Use native mode only for trusted tasks, source and check programs.

## Optional Docker runtime

Probe `docker info` and `docker image inspect YOUR_IMAGE`. Copy `assets/runtime.docker.example.json` into the project's temporary campaign directory and replace every marked value. Use `backend: "docker"` (or an image-only legacy runtime), an immutable image reference ending in `@sha256:` plus its full digest, explicit model identities, exact `claudeVersion` and finite limits. The image must contain Node18.19+ or a newer major, Git, that Claude Code CLI, project/framework helper toolchains and offline check dependencies. The runner neither pulls an image nor installs a toolchain.

Docker reads `ANTHROPIC_API_KEY` from the environment; it mounts no subscription profile, host home/source checkout or Docker socket. The image is trusted and must contain no credentials or personal configuration. Only read-only inputs are mounted. Work uses a fresh 512 MiB temporary workspace and bounded home; root filesystem is read-only, capabilities are dropped and process/memory/CPU limits apply. Grading has no network; solve/review containers have a provider-call network. The key exists inside those containers, so loop limits do not prevent out-of-band calls with it. Docker requires explicit legacy assessment; skilled reviewer capability/report collection is currently native-only and rejects unsupported Docker preparation. Three legacy pairs with 2/0.5 USD solver/judge allowances configure 18 USD of loop allowances, not a billing guarantee. Use the provider's own spending controls where needed.

Both modes exclude the benchmark's own cases and mechanics-test answers across framework mirrors. Selected source and prompts reach the model/provider: omit unauthorized secrets/private data. Known local/secret-file exclusions are not a general secret scanner. Docker candidate code stays in containers; the host collector validates bounded data.

## Portable commands

These Node commands are identical in PowerShell and POSIX shells; quote paths containing spaces. Replace example input/run paths with those actually prepared. `--framework` optionally selects the framework installation for fictional/bootstrap cases; a committed consumer installation takes precedence.

```text
node .claude/skills/framework-benchmark/scripts/benchmark.cjs prepare --case .claude/skills/framework-benchmark/cases/dependency-planner/greenfield.json
node .claude/skills/framework-benchmark/scripts/benchmark.cjs prepare --case tmp/benchmark/consumer-case.json --project .
node .claude/skills/framework-benchmark/scripts/benchmark.cjs prepare --case tmp/benchmark/consumer-case.json --project . --host codex --model YOUR_EXPLICIT_MODEL
node .claude/skills/framework-benchmark/scripts/benchmark.cjs prepare --case tmp/benchmark/consumer-case.json --project . --runtime tmp/benchmark/runtime.json
node .claude/skills/framework-benchmark/scripts/benchmark.cjs run --run tmp/framework-benchmark/run-ACTUAL_ID
node .claude/skills/framework-benchmark/scripts/benchmark.cjs report --run tmp/framework-benchmark/run-ACTUAL_ID
node .claude/skills/framework-benchmark/scripts/benchmark.cjs compare --campaign tmp/framework-benchmark --out tmp/framework-benchmark/comparison
node .claude/skills/framework-benchmark/scripts/benchmark.cjs compare --runs tmp/framework-benchmark/run-A,tmp/framework-benchmark/run-B
```

The first three examples use native discovery; the fourth uses an explicit native or Docker runtime file. Replace `YOUR_EXPLICIT_MODEL` and actual paths before running. `prepare` emits the actual run directory, frozen runtime identities and any configured loop allowances. It calls no model. `run` calibrates checks before solvers and executes once; exit zero means complete experiment evidence, not a framework win. Blocked/inconclusive execution exits nonzero and retains a report. `report` regenerates summaries from saved state without another model call. `compare` reads several saved runs (a comma-separated `--runs` list, or every saved `run-*` folder under `--campaign`) and writes `comparison.json` and `COMPARISON.md` under the project's `tmp/` or `temp/`, also without a model call.

## Evidence and recovery

Each run keeps frozen base/framework/checks, source revision and identities, result/summary reports, solver/check/reviewer observations, anonymous application artifacts, setup artifacts and nullable measurements. An accepted full quality assessment lives in each attempt's `quality-assessment.json`, including every criterion rationale and finding; campaign state keeps numeric scores, its relative path/hash and reviewer identity/metrics. Report links open that full evidence without multiplying narrative inside the bounded state file. Older saved embedded assessments remain readable. Requested and observed model identities stay separate until native metadata proves the latter. Claude token usage sums the result's per-model usage, which includes subagents; the top-level `usage` field covers only the main session and is used only when no per-model usage is reported (`usageScope` in the observation records which). Native subscription charges stay null/unknown; any API-equivalent estimate is labeled separately. Setup artifacts have separate receipts and are excluded from blinded application review. For a reusable template, preparation `configuration.wallMs` is the total observed investment; `solverWallMs` is its inference subset, and unavailable usage stays null. Read [complex-corpus.md](complex-corpus.md) when inspecting archive identity and exact remaining input-cleanup work. Inspect report.md, result.json and the attempt observations for exact failure/fidelity and cleanup evidence.

Generated root instructions may refresh as setup. Installed skill/hook bytes and native control membership are checked at collection; new local overrides invalidate treatment. These are final-snapshot observations, not continuous attestation. Claude engagement requires a successful native Skill result; a required `workflow-*` also counts when a successful `start-workflow` call names it as its first argument (the framework's own activation route), at that position for setup ordering, and is reported separately as an activated workflow rather than a skill load; Codex engagement requires successful literal POSIX or PowerShell reads containing the complete required skill file, with CRLF/LF transport differences normalized; partial, failed or transformed reads cannot substitute for a complete load. Neither receipt proves every workflow gate ran.

Full solver metadata, engagement lists and per-model usage stay in `solver-observation.json`. Central solver skill lists are previews of at most 64 names, labelled with exact counts, completeness and a full-observation path/hash; per-model usage points to that observation. Treatment fidelity is calculated from the complete response, including required skills beyond the preview. Central journey metadata contains only declared coverage/identity summary fields and a path/hash for the complete trace manifest. The observer still receives every retained receipt and page. These summaries keep growing diagnostics out of repeated campaign checkpoints without discarding the detailed evidence.

Inputs and control code are sealed; changed inputs require a fresh prepare. The sealed runner fingerprint covers this skill's `lib/` and `scripts/` plus the shared hook and script libraries, so another session editing the same checkout voids a running campaign. When the checkout is shared, copy `.claude` (without nested worktrees) under the project's `tmp/` and invoke that copy's `scripts/benchmark.cjs` from the project root for every prepare, control, run and compare. Run cases one at a time, controls before solvers, and stop before any solver if a control is ungraded; do not run test suites or other heavy work during a campaign, because it distorts solver time and can time out worktree checkouts. Attempted runs are never replayed. Retain application/setup output and observations before removing exact owned worktrees; preserve partial evidence and cleanup receipts. Private profiles are removed in cleanup. Cleanup uses recorded ownership, never the original checkout or a broad Git prune/reset. A process/host death can leave resources: inspect recorded owned worktree paths or `framework-bench-*` containers, preserve results, and remove only verified owned resources. Cleanup failure remains visible. Handled interruption saves interruption.json with exact retained worktree paths, clears private profiles and stops owned process trees; recover those paths before choosing an explicit cleanup. Known context/task-budget failures stay failed work when identity is observed; unavailable login/provider and unknown failure causes remain invalid.

Each owned-worktree Git command may take up to two minutes, because a full checkout of a large snapshot on a busy machine with on-access antivirus scanning exceeded 30 seconds. Collection bounds: 12,000 files, 128 MiB snapshot total, 4 MiB per file, depth32 and 32 MiB exported application patch; 1–20 pairs, 1–500 turns/actions, up to one hour per solver and five minutes per check. Unsupported links/submodules, case-colliding names and escaping paths fail closed. Collection bounds are not native disk quotas. Grading starts fresh and uses provisioned dependencies or explicitly authored offline setup.

## Execution journey evidence

Each attempt retains `journey-trace/manifest.json`, ordered `events-*.jsonl` pages, `journey-observation.json` and `journey.md`. An accepted full account also lives in `journey-story.json`; campaign state retains its relative path/hash and observer identity/metrics, so detailed stories do not multiply inside the bounded state file. The Markdown view encodes observer text as inert content; the structured account preserves its original text. Native recording writes public events as the CLI emits them, before completion/cleanup. Docker reconstructs its public record from the completed CLI stream and labels that timing limit. Handled interruption may leave an unfinished live trace; preserve it and mark its missing completion rather than inventing a full story.

A separate fresh read-only model session interprets the recorded journey after the solver ends, avoiding concurrent observer inference or feedback that could change the solver. Its chronological story and eight aspects cover task understanding, planning, context use, implementation, testing, review/recovery, workflow/skills and efficiency/limits. Statements cite retained relative paths and lines, with observed/inferred/unknown distinctions. The observer receives the task and public record, not private account/session files. Hidden reasoning blocks are excluded. The end-product assessor receives neither the trace nor its interpretation and stays anonymous.

The manifest records event counts, retained pages/hashes, native receipt timestamps relative to capture start (completed-stream timestamps remain unknown), terminal coverage, malformed/unsupported events, truncation, supported successful skill receipts and capture limits. Public Claude records preserve exposed enclosing-run identifiers separately from tool invocation identifiers; explicit root identity stays distinct from unavailable metadata. Native skill receipts remain load evidence, not proof of every workflow gate. Hook installation alone never proves hook execution; unexposed helper-agent actions and provider internals remain unknown. Commands and their exit/output are inspectable, but command-level success is not an invented number of passed tests.

Trace limits are 20,000 selected public records and 16 MiB total, 1 MiB per page and 60,000 characters per record detail. Every clipped/dropped record is counted and incomplete/unsupported coverage stays explicit. Existing solver/output/time/action limits still apply. Observer schema and citations are validated locally; real locations do not by themselves prove factual entailment or calibrated judgment. Missing, malformed, reused, mismatched or modifying observers remain ungraded, leaving the captured record readable. The observer error names the first failed condition (session failure class such as a provider refusal, model, identity, reuse or modified evidence). A run with missing required observer evidence is inconclusive; objective work/check outcomes are preserved.

Reports expose observer wall time, reported input/output/cache tokens and nullable cost separately. Maximum configured loop allowances are `pairs × 2 × (solver allowance + (1 + maxPasses) × judge allowance)` for skilled assessment, or two judge allowances per arm for legacy. Separate template preparation and reviewer controls are additional investments outside that campaign maximum. Neither allowances nor API equivalents become subscription billing. Compare stories against independent checks and artifacts: extra steps, plans, review claims and verbose explanations are not quality scores. Retain neutral/negative stories and explain uncertainty before recommending framework changes.

## Skilled assessment evidence and controls

New preparations default to the skilled native policy in [cases.md](cases.md), freezing an `evaluatorHash` and neutral toolkit. Both arms receive identical review capabilities: the required role, appropriate skills and complete shared review protocols. Default discovery uses code-quality-review plus integration-test for implementation or why-review for plan/decision/review work; every second pass uses terminal why-review findings validation. Read [complex-corpus.md](complex-corpus.md) when qualifying task scope, preparing source/context archives or running known healthy/defective controls before solver answers.

Each attempt retains `quality/pass-N/assessment.json`, `stage.json`, `observation.json`, public `review-trace/` and optional bounded `reports/`. Required role/skill receipts, identity, candidate/toolkit integrity, collection and cleanup are inspectable per pass. Claude assessors use native Read for the complete role file and native Skill loading; Codex uses complete literal file reads. Claude's Read output frames each line with its number followed by an arrow or, in current CLIs, a tab; the parser strips either frame, and a role file longer than one Read must be read in contiguous, in-order parts (a skipped line or reversed parts is not a complete read). The assessor prompt states these loading steps first, before the long protocol block, and repeats them last, because Claude assessors given a structured-output tool otherwise answered without loading and were rejected. Public reports are at most64 files,2MiB total,1MiB per file and8 levels. A final accepted assessment lives in `quality-assessment.json`; campaign state keeps numeric scores, distinct confirmed causes by severity, rejected/unresolved/new-LOW counts, compact per-pass identity/metrics and evidence references. Full claims, criterion rationales and decisions remain in the retained files rather than repeated in central state.

Scores, findings and validation reasons start with an existing application relative `path:line` or `path:start-end`, then whitespace and the inspected evidence. Claude reviewers receive that start-of-string rule as a structured-output schema pattern, so a prose-first answer is corrected at submission; Codex keeps the unchanged schema and the same controller check afterwards. Reviewers are told to take cited line numbers only from a line-numbered view: a Claude reviewer that read a 64-line file with `cat` cited lines 58–66 for a correctly identified defect, and that range voided the assessment. A span uses positive inclusive endpoints in order within that same file; missing files, reversed spans and endpoints beyond the artifact remain invalid. Only a wholly empty artifact permits `EMPTY:1` with zero scores.

Every prior finding receives one validation decision with this evidence, for confirmed, rejected and unresolved verdicts alike. Confirmed manifestations may map to one retained cause; rejected/unresolved claims never count as confirmed. New consequential claims require a fresh third pass when allowed. An unresolved consequential claim, newly introduced consequential finding at the cap, missing role/skill/freshness proof or any candidate/toolkit change leaves assessment ungraded. Empty discovery still receives a separate validation pass. This is bounded independent checking, not candidate repair, consensus ground truth or continuous filesystem attestation.

`assess-control --run PREPARED_RUN --candidate ANONYMOUS_ARTIFACT --out tmp/controls` uses the same frozen instrument without a solver or supplied expected verdict. It requires an unattempted prepared native skilled run, retains a separate `control-*/result.json` with full pass artifacts, and leaves the campaign prepared. The maintainer compares results with separately recorded expectations; an exit-zero completed assessment does not itself certify control accuracy. Every control's time/usage/cost belongs to calibration overhead. Already saved legacy cases without an assessment field preserve their original single-pass interpretation; readable history is never relabeled as skilled/validated evidence.

## Compatibility and proof limits

Built-in solver/assessor adapters target native Codex, native Claude Code and Claude Code in Docker Linux containers. OpenCode execution is not supported. Intended support is separate from observed compatibility: mechanical tests, login checks and tiny inference probes do not establish a completed live campaign or framework benefit. Each CLI, platform, model and runtime lane needs its own receipts; unavailable or unexecuted lanes remain NOT RUN.
