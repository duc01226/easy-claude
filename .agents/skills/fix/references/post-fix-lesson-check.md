# Post-fix lesson check

> Read when a fix has passed its review, before the single verify step: standalone `$fix` after its `$why-review` sign-off, and `workflow-bugfix` after `$workflow-review-changes` converges. Running it before the verify keeps the verify last (`SYNC:verify-last-order`), so a lesson saved through `$learn` lands before the final green run. This file is the one owner of the check for both. A `$fix` step nested under any other caller records the bug class, the sibling sweep and any lesson candidate in its report and hands them back instead of asking.

**Purpose:** a fixed bug often belongs to a class that will strike again elsewhere in the project. Name that class, find the copies it already has, and offer the strongest guard that stops the whole class, so future work cannot repeat it rather than merely being told not to.

1. **Classify the bug class**, apart from its business subject, with the root-cause `file:line`: test reliability (flaky, order-dependent, shared state, timing), code quality (unchecked null or lookup, boundary, swallowed error, duplicated rule, hidden coupling), performance (unbounded loop or query, query per row, missing index, cache misuse), concurrency (race, missing await, retry storm), contract drift (spec, API or schema against code), configuration or environment, security, data integrity, build or tooling.
2. **Sweep sibling instances.** Search the project for the same pattern, not the same business subject: cite the query, the count and each `file:line`. Report them; never fix them silently outside this change. A copy that a comment justifies is still a sibling, and a workaround found on the way is reported, never copied. Each sibling becomes a follow-up the user decides on, or an entry in the baseline of the guard below.
3. **Look for a generic lesson.** Strip every feature, entity, customer and file name, then ask which rule would have prevented this class elsewhere. Keep a candidate only when all three hold:
    - **Generic** — it names no business rule (a business rule belongs in the spec and its tests, not in a lesson).
    - **Likely to recur** — the sweep, sibling code or past fixes show the same pattern, or the class is common in this stack; cite what you searched.
    - **Not already covered** — no lint rule, type check, test or hook catches it, and the project's lessons and reference docs do not already say it (search them).
4. **Pick the strongest guard, structure-first** (the tiers of `$learn`'s Prevention Depth Assessment): make the class impossible by design (a type, a wrapper, a structure), else a lint rule or architecture test whose message names the fix and whose frozen baseline holds the swept siblings (green when it lands, the next copy fails), else a test, else a hook; a prose lesson through `$learn` comes last. Note why each stronger tier does not fit.
5. **Confirm with the user.** For a surviving candidate, ask through the host question tool whether to save it, the chosen tier first as `(Recommended)`: `Add the <tier> guard`, `Save with $learn` or `Skip` when the tier is structural; `Save with $learn` or `Skip` when the walk ended at prose. A structural pick is planned as its own reviewed change (`$plan`), never folded silently into this fix. On `Save with $learn`, invoke `$learn` with the generalized lesson, its bug class, the evidence and the tier walk already done (so it does not offer a declined guard again); `$learn` chooses the carrier, runs its own confirmation and saves.
6. **Record the outcome** in the fix or workflow report: `Siblings: <count> — <query>`, then `Lesson: <class> — guard planned (<tier>, <owner>)`, `Lesson: <class> — saved via $learn (<carrier>)`, `Lesson: <class> — declined by the user`, or `Lesson: none — <reason>` (business-specific, one-off, already caught by <check>, already written at <path>).

**Worth offering:** shared mutable fixtures make tests flaky → a test-isolation lint rule or fixture factory, with a lesson only if no tool can see it; an unchecked lookup crashes → a lookup wrapper that returns an explicit "missing" result; one query per row slows a page → an architecture test that forbids data access inside a loop body. **Not worth offering:** a business rule the code violated, a one-off typo, a rule a check already enforces.

**Limits:** never save without the user's answer; the check never blocks or reopens the fix. A sub-agent or headless run cannot ask: it records the candidate in its report and returns it to its caller, which asks. This check covers the defect's class; the Lesson Extraction Gate still covers the assistant's own reasoning mistakes — when both find a lesson, ask about them in one question.
