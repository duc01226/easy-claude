# Verify receipt before a commit

Read when the commit skill runs its checks. The verify receipt proves that the project's configured lint, type and test commands passed on the exact tree being committed; the commit gate reads it under `reviewGate.verify` (default `warn`, `enforce` refuses the commit, `off` skips the check).

1. **Is verify configured?** `node .claude/hooks/lib/verify-receipt.cjs plan` lists the command keys (`testing.commands.verify`, or `lint`, `typecheck`, `affected`, plus `build` with `reviewGate.verifyBuild`). Nothing configured and the mode is not `enforce` → skip this reference. A missing key is reported unavailable, never passed: offer `$project-config` to fill it, or set it to `"none"` when it does not apply. `plan` prints each command's text: when the project config records no `reviewGate.verify` choice yet, show those commands to the user once before the first run, because keys that existed before verify may hold a fixer (`--fix`, `--write`) rather than a check.
2. **Stage first, then verify.** The receipt binds the working tree, so it matches the commit only when the working tree holds exactly what the commit will hold. Other unstaged or untracked work that this commit leaves out makes the trees differ: the commands ran on files the commit does not contain. Set that work aside first, or record why verification cannot cover this commit (step 5).
3. **Reuse or run.** `verify-receipt.cjs check` → `PASS` for the current tree is reusable evidence. Otherwise `verify-receipt.cjs run`. When `plan`'s `totalBudgetSeconds` is longer than the host's foreground command limit, start `run` in the background (or with a timeout at least that long) and read its JSON when it finishes; stopping the runner stops the commands it started. It runs each command within its time budget and reports only failures that are not in the committed baseline (`.verify-baseline.json`). Fix each new failure at its root cause, then run again. Never add a new failure to the baseline to make the gate quiet.
4. **Prune before the review.** When the run reports baseline entries that now pass (`baseline.prunable > 0`), run `verify-receipt.cjs prune`, then stage `.verify-baseline.json` with the change. The prune re-issues the receipt for the pruned tree, so the commit still matches. Any other edit after it needs a new run. Prune before the review snapshot, so the review sees the staged baseline file.
5. **Cannot run here, or the user asks to bypass?** A timeout or a tool this environment cannot install is `ENVIRONMENT-BLOCKED`, never a pass. Under `enforce`, `verify-receipt.cjs skip --reason="<10-500 characters>"` records it for this tree only; it is refused when a run on this tree found new failures, which are fixed, not skipped. When the user explicitly asks to bypass verification, honor it: add `--user-requested` with their words as the reason, which also works over found failures and records the verdict it overrode. Never add it on your own judgment. Name the reason in the report; never describe a skipped run as passed.

The first baseline is a deliberate step, never part of a commit's checks. `verify-receipt.cjs baseline-init` freezes today's failures, once, with the user's agreement. It refuses to re-freeze a command it already proves unless `--replace` is given.
