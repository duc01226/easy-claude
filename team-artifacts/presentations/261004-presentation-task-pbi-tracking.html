Task and PBI tracking / Proposed portable platform feature

A daily-use demonstration for a small repository team. From an idea to accepted delivery, with a current project report.

How to watch and explore

Watch
Press Play guided demo. Pause anytime. Slow = 35 s/frame, Normal = 25 s/frame, Fast = 12 s/frame.
Explore
Chapters jumps to a story. Replay story returns to its first frame. Next and Previous step through it.
Keyboard
Left/Right, Home/End; Up/Down, PageUp/PageDown and Space scroll long frames before advancing. Shift+Space goes back.
Present
Notes opens the talk track. Escape closes Notes. Tab into notes makes scroll keys move only the notes; Tab or click outside to return.
Window
All slides provides a complete overview; Escape closes it. Full screen and Dark theme are optional.
Read safely
Playback pauses when you navigate, open notes/overview, leave the tab, or a frame needs scrolling. Reduced motion uses manual navigation.
Print/offline
One slide per printed page; speaker notes and controls are excluded. With JavaScript off, every slide is readable in order.

These are narrated plan frames, not embedded product screens. There are no product hotspots or simulated save buttons.

A typical day with the tracker

09:00 / team lead
Open current project status. Read remaining outcomes, blockers and proof freshness.
09:15 / developer
Pick the ready CSV PBI, name it explicitly and start work directly or with a workflow.
11:30 / product owner
Save a new idea or resolve the column decision; requested changes keep their own receipts.
14:00 / developer
Record a blocker or move finished implementation to verifying.
16:00 / QC and owner
Attach applicable current evidence, then accept the delivered outcome.
16:30 / team
Open the refreshed status. Review new scope and stale proof before choosing tomorrow’s work.

Times and roles are an illustrative routine. The team can use ordinary prompts; it does not need to run a full workflow for every action.

Count outcomes and current confidence separately

Customer data export contains three delivery PBIs: CSV download, filtered export and Excel download.

Delivery unit
One unique PBI in the selected scope. Endpoint, UI button and tests are child execution work.
Accepted
4 of 10 PBIs accepted. Six delivery outcomes remain.
Current verification
One accepted receipt is stale: 3 of 10 currently verified; one accepted item needs re-verification.
Health
An owner may record a dated “at risk” reason. A percentage does not invent health or ETA.
Scope
Canceled work is excluded and disclosed. Known planned scope is not the complete vision.

Accepted delivery history remains stable when proof becomes stale. Explicit reopening changes delivery counts.

Start small, automate the proven paths

Selected pilot
A0: extend current Markdown artifacts. Explicit validated updates, lifecycle, proof, groups, stale checks and offline table/details/print.
Next release
Bounded linked feature/implement-spec activity and review integration; initialized supported reports refresh after permitted saves.
Later
Optional Kanban projection, retained-history flow metrics and extra adapters only after measured need.
Alternatives
Backlog.md adapter if preservation/maintenance favors reuse; GitHub/Linear when remote tickets are authoritative.
Priority
No authored implementation PBIs are prioritized yet. CSV first is only the demonstration’s example sequence.
Boundary
No universal watcher, hosted editor, automatic ticket for every prompt, distributed lock or automatic acceptance.

Know where each artifact belongs

team-artifacts/ideas/
Draft ideas and future intent; outside delivery counts.
team-artifacts/visions/
Goal grouping and known planned scope.
team-artifacts/epics/
Included PBI IDs, scope revisions and owner health notes.
team-artifacts/pbis/
Canonical portable delivery records and durable acceptance summaries.
team-artifacts/pbis/stories/
Optional user-facing slices supporting a PBI; no second delivery count.
team-artifacts/tasks/
Enabling execution work: endpoints, tests or investigations.
plans/ and docs/specs/
Plans and canonical specs retain their own owners and roots.
tmp/reports/task-pbi-tracking/
Disposable HTML, metadata, diagnostics and execution evidence.

Folders are created lazily for authorized saves. State changes update metadata; files do not move between status folders.

Configure storage without creating a second tracker

Portable roots
docsRoots.teamArtifacts.path can relocate the tree, for example to docs/work-items/. docsRoots.plans.path and specRoots.business.path retain their separate roles.
Native profile
Proposed optional versioned taskTracking configuration resolves native roots, guide, labels, policies, capabilities and report scope.
Machine rules
Trusted project-owned parsers, validators, writers and renderers implement native invariants. Complex formulas are not executable config strings.
Skill guidance
Project protocol overlays add instructions. They cannot enforce a serializer invariant or waive access, proof or workflow gates.
Migration
Changing a path/profile is not a migration. Preview, preserve and separately authorize actual record changes.

Existing root settings are reuse targets. The taskTracking section and exact tool/schema keys are proposed, not available commands.

Ordinary prompts reach the right owner

  • Prompt: “Open the project status report” or “Update the CSV PBI”.
  • Concise skill/context/index pointer resolves the project tracking profile.
  • Read the shared team-artifacts guide only when the task needs it; native projects then follow their own guide.
  • Resolve the exact record or report capability through one owner.
  • Run the permitted deterministic operation; return actual saved/generated/opened outcomes.

Planned shared guide: .claude/docs/team-artifacts/README.md. It is not shipped yet. Discovery is passive context, not permission to scan or mutate everything.

Pointers benefit capture/PBI, spec/plan/design, implementation, review/report, artifact workflows, presentations, architecture inputs and configuration/documentation skills.

No prototype or design available for Task/PBI tracking

This deck demonstrates the selected plan through narrated requests and saved footprints. It does not show an implemented tracker application.

  • The proposed project report will support overview, searchable list, filters, item details and print.
  • Existing native Orient-One UI remains consumer-owned. Its report formulas and records are reused through a proved adapter.
  • Product UI, schemas and executable tool names still require implementation and validation.

The project report is an honest snapshot

Default destination
tmp/reports/task-pbi-tracking/project-status.html with disposable project-status.meta.json.
First request
Create missing output from permitted inputs. No ticket creation, extra workflow or create-confirmation.
After supported saves
Refresh initialized HTML once per bounded operation/batch, without opening another viewer.
External edits
Next allowed open/check rereads and refreshes. Browser reload only reloads the saved snapshot.
Restricted access
No-write can open existing dated output. Missing/denied/partial reads remain unavailable or partial, never an empty 100%.
Preservation
Unknown authored collision is preserved; late older refresh cannot replace a newer snapshot; failure keeps the last good view.
Separate scopes
Scoped exports have separate destinations. Filters retain the project denominator; historical snapshots stay historical.

Reused authority

What QC must prove before the feature ships

  • New accepted Done requires actual scoped acceptance and current applicable proof.
  • Repeated operations do not double-apply; conflicts preserve teammate edits and custom prose.
  • Direct, skipped-skill, disabled-tracking and manual-edit cases keep their intended authority.
  • Report missing/stale/collision/denied/failing/concurrent cases preserve valid records and honest scope.
  • Native alias counting, immutable archives, owner footprints and worktree/main separation follow consumer owners.
  • Offline report keyboard, focus, contrast, narrow/zoom and untrusted content behavior are validated.
