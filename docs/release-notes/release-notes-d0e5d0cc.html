Changed

Every workflow states its goal and marks what cannot be skipped

Each workflow now opens with a one-sentence goal and the results it must prove: tests pass, the review converged, the spec is synced when behaviour changed, the root cause is traced for bugs, and the run closed. Steps in your task list carry a tag.

  • Gate steps always run.
  • Core and optional steps may be skipped, merged or reordered when the goal allows it.
  • Every deviation writes one line with its reason to the run's skip log, so you can see what was cut.

The bug-fix workflow, for example, has 4 gate steps, 9 core steps and 2 optional steps.

A run can't close without proof

The closing step first checks evidence for every required result. If any is missing, the run stays open, and you are told which result is missing and which step produces it. New

Build what your spec already says: /workflow-implement-spec

When the behaviour you want is already written in a spec or test-case set, this route skips re-writing the spec and goes straight to building it. Tests, review and close still run as gates.

If the gap check finds the spec vague, contradictory or missing what you asked for, it stops before planning. It then asks you to clarify, or to switch to the full feature workflow.

How: /workflow-implement-spec. The assistant can also pick it when the behaviour you ask for is already in a spec.

New · on by default

A progress check-in every 500,000 tokens

Each time a session's non-cached token use crosses another 500,000, the assistant stops at the next step, gives you a short progress report and asks whether to go on. It skips the question if you already told it to keep going. Sub-agent work counts toward the total. The check-in never blocks anything.

Tune: hooks.tokenBudget.checkpointTokens (50,000 – 20,000,000) · Off: hooks.tokenBudget.enabled: false

Improved

Skills are about 40% smaller, and shared rules are sent once

Skills used to repeat every shared rule inside themselves, so loading three skills paid for the same rules three times. Now each skill carries a one-line pointer per rule. The full text arrives once per session, when the first skill that needs it loads. If that delivery is ever missed, the pointer names the file to read, so no rule goes silent.

  • The biggest saving comes on the second and later skill loads in a session. The first load is only about 5–14% lighter, because the rules still arrive that time.
  • The five review skills keep every rule written inline, so reviews never depend on delivery. They still shrank 11.6%, because mode-only sections now load on demand.

Known trade-offs

  • Codex shell commands are a little slower. Six quick-exit checks run on each shell call, about 1.5 s median on the test machine. This was measured once on Windows 11 and has not been re-measured.
  • The token check-in and usage report read Claude Code sessions only. On Codex and OpenCode the check-in most likely stays silent.
  • Rule-following after the new delivery has not been scored yet. Tests show the rules are delivered. The before/after compliance review is scheduled but has not run.
  • No saving is claimed yet for the lean route. Its token cost has not been measured against the full route.
