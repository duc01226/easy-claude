Before any mockup, design spec, screen review or UI code, Claude writes a short journey report: who uses the screen, their job, the main journeys ranked, and the steps of each. It reads your design system, then designs.

At the end it walks each journey through the result and checks steps, clicks and wayfinding. A small tweak gets a few lines; a new flow gets the full report.

Before

You asked for a leave-approval screen. Claude went straight to layout and components.

It looked tidy, until managers had to open another page to see who else was off.

After

You first read who the manager is, their job, and the step where they check who else is off. You fix a wrong guess before any pixels exist.

You review the thinking first, so reviewing the look is quicker.

How to useAlways on for UI work. If the main user, their job or the success outcome is only a guess, Claude asks you first. With nobody to ask, it notes the guess and continues.

ChangedDefault change

Reviews scale with the change, and fixes go straight to the point

Before: every review

  1. Five of seven specialist reviewers ran on every change.
  2. Findings went through plan → plan review → execute.
  3. It stopped to ask "switch workflow?" and "next steps?".
  4. Nested reviewers could ask questions or edit files.

After: sized to the change

  1. It sizes the change (XS–XL) and its risk first.
  2. Architecture, performance, security and production-readiness reviewers join only when relevant. The test review always runs.
  3. Each finding is checked, traced if unexplained, fixed, then re-reviewed.
  4. Nested reviewers only report.

Small changes get a quick review; large or risky ones still get every specialist. Round limits and the clean-review-before-commit rule are unchanged.

How to use/changes-review for a quick review, /workflow-review-changes to review and fix. The report is now tmp/reports/changes-review-*.md.

Ship a change

A reviewed, tested, green pull request in one command.

New

/pull-request takes your work from "done coding" to "ready to merge"

Claude Code⚠ Illustrative session, not a real transcript
> /pull-request
● On main with uncommitted work → created branch fix/export-retry
● Staged 7 files · left out .env.local (looks like a secret)
● Review of the whole branch, fix loop
    round 1: 3 findings → checked → fixed
    round 2: no new findings
● Tests: all passing
● Committed through the commit skill · pushed · opened pull request (ready for review)
● CI: lint ✓   unit tests ✗
    → read the log, traced the cause, fixed, re-reviewed, pushed
    unit tests ✓
✓ Ready to merge. You review and merge.
  Report: tmp/reports/pull-request-<date>-fix-export-retry.md

On your main branch, Claude creates a feature branch. It stages everything except secret-looking files, reviews and fixes the whole branch, runs tests, commits, pushes and opens a ready-for-review PR.

It then fixes failing CI checks until they are green and stops at "ready to merge". Typing the command is your go-ahead; it never merges, force-pushes or pushes to main.

Before

  1. Create a branch.
  2. Review, then /commit.
  3. Ask for a push and a PR.
  4. Watch CI.
  5. On failure: paste the log, fix, review, commit, push again.

You were the glue between five tools.

After

  1. Type /pull-request.
  2. Come back to a reviewed PR with green checks.
  3. Merge.

Like handing the change to a careful colleague.

How to useType /pull-request or ask to "open a PR". It asks nothing and stops only on a real blocker, such as a failure it can't fix after three tries or no GitHub sign-in. It targets main, Orient One's default branch.

Technical details

Under the hood: internal changes
  • Git confirmation prompts removed for git branch -D, git checkout -- and git restore, for more agent autonomy. CLAUDE.md still tells the agent to confirm before discarding uncommitted work.
  • All 21 workflow guides share one template (20 rewritten, 1 new). The existing guides shrank from 4,939 to 3,844 lines (−22%), and /changes-review from 2,397 to 1,317 lines.
  • New modes: --report-only on six reviewers, --prove-tests on the integration-test reviewer, and /fix --target=review.
  • The new journey-gate protocol is carried by the design, planning, mockup and review skills and the UI/UX designer agent.
  • New config key pullRequest.targetBranch (default main).
  • Tests: 2 new suites. Two limits loosened: round3-prompt-contract.test.mjs:390 (exactly 5 → at least 2 copies) and a schema-output cap (590 → 620 lines).
  • Also: the fix loop counts /fix and /code-simplifier edits, doc-impact-map.cjs got the symlink fix, the docs were updated, and 61 generated copies were regenerated.
