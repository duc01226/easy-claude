### P01 — High: review convergence is not required for report-based closure

Evidence: [workflow-end gate](/Users/duc.dangphuoc/GitSources/easy-claude/.claude/skills/workflow-end/SKILL.md:64) versus [executor invariant](/Users/duc.dangphuoc/GitSources/easy-claude/.claude/skills/start-workflow/SKILL.md:219). The executor says gate outcomes never flex and the review must converge. When the receipt check reports changed content without a matching review receipt, workflow-end accepts a cited report from a satisfying occurrence. It explicitly says to continue and “never block or ask when a report is cited.” A failed or stale report is recorded as such and repeated in the close message, but does not block closure.

Trigger: a changed run relying on a report rather than a receipt, with a nonconverged verdict or a report older than the last change-producing occurrence. Consequence: the `review-converged` outcome can be declared satisfied while its evidence says it is not. This finding concerns the fallback’s validity check; it does not assert that receipt hashing is broken.

Correction: require an accepted final verdict for the declared gate and freshness against the reviewed target, not merely a report path. Keep diagnostic audit completion distinct from implementation convergence: a completed architecture audit may legitimately report defects, whereas an implementation’s convergence gate requires resolution. Preserve unsupported-host fallback but enforce the same evidence predicate there. Add an executable gate/report-state check where the host can enforce it.

Trade-off: stronger closure may keep previously closable failed/stale runs open; **WORTH IT** because it restores the existing invariant rather than adding a new gate. No repair was performed or new product policy approved. Confidence: **99%**. Drift: **SPEC-STALE** closure instructions relative to executor and consuming gate contracts. Test feedback: fixtures for current accepted, current rejected, stale accepted, missing report, clean tree and unsupported-host report fallback; rejected/stale evidence must not satisfy implementation convergence. Bind scenarios to the configured canonical owner/carrier and test mapping rather than assuming a universal §8 representation.

## Recommended repair order

1. **Restore acceptance and handoff correctness:** P01, D1, RS-1, EX-04, D4. Exercise producer → consumer → rejected-output repair → final acceptance, not only text/phrase checks.
2. **Protect repository state and command results:** EX-06, EX-07, EX-08. Run probes in isolated fixture repositories; test the failure of the mechanism under test and assert original HEAD/index and command status remain intact.
3. **Repair routing and representation:** EX-01, RS-6, EX-03, D5, D6. Use table-driven tier tests and supported/unsupported carrier fixtures.
4. **Remove conflicting and irrelevant requirements:** EX-02, EX-05, D2, RS-2, RS-3; then low-severity consistency fixes D3/RS-5. Keep one authoritative rule and align summary/body/reminders. For D2, the minimal consistency repair is to align reminders with the earlier procedure’s conditional fresh-review rule; adopting a new unconditional policy would be a separate decision. This consolidating recommendation supersedes the lane report’s open policy choice.

All corrections above are recommendations for later implementation. A new policy, schema migration, production collation change or extra mandatory quality gate should be treated as a separate design choice rather than silently bundled into a consistency repair.

## Cross-cutting gaps and positive practices

**Behavioral evaluation gap.** The framework already has a [pressure-testing guide](/Users/duc.dangphuoc/GitSources/easy-claude/.claude/docs/skills/pressure-testing-guide.md) describing no-skill baselines and with-skill pressure cases. The audit did not find a repeatable model-executed suite spanning the workflow skills with positive/negative activation, unsupported-host cases, repair loops and with/without-skill quality/cost comparisons. This is a discovered assurance gap, not proof that no manual experiments exist. Turn the guide into versioned scenarios/results tied to skill content, model/runtime and task family. Start with the 21 defect paths and a small benign control set. Measure successful outcomes, unintended actions, recoverability, total tokens and time; do not optimize instruction length alone.

**Context cost opportunity.** The 94 roots contain 2,974,339 characters total; 10 of the 46 direct roots exceed 500 lines and 31 exceed a rough 5,000-token estimate (characters/4). These are static corpus measurements, not one-run context sizes. Shared protocol delivery and selective reference routing may reduce actual loads. Move duplicated stable policies to one owner and load mode-specific details only when needed, then measure quality and cost before broad compression.

**Profile consistency debt.** workflow-feature still describes §8 TC duties and design-spec’s early steps presume §6 sections/default IDs, while their shared contracts support native artifact profiles. Existing profile authority prevents asserting an unavoidable duplicate registry. Align local instructions with that authority so native callers do not receive mixed guidance.

**Security/portability assurance limits.** Prompt text is not enforcement. Secret-output redaction, malicious-source handling, offline browser isolation and cross-host tool adaptation were not penetration-tested. Offline HTML export explicitly documents local-file/unsandboxed limitations; that is not a newly proven vulnerability. Static portability checks cannot establish equivalent behavior across Claude/Codex/OpenCode runtimes.

Several practices are sound: deterministic manifest resolution, explicit outcome/role metadata, config-derived paths, mode dispatch with selective references, report-only review boundaries, provenance/evidence requirements, bounded repair protocols, generated-mirror ownership and pressure-test guidance. These strengths did not prevent stale repeated rules and producer/consumer contradictions, which are the dominant retained pattern.
