# Bug-class prevention (`/fix --mode=prevent`)

> Read when the prevention task runs: the `bugfix-prevent` gate of `workflow-bugfix` (right after `/fix`, before the review), the `prevent-recurrence` step of `workflow-review-changes` (after `fix-findings` repaired a behavior defect), or the prevention task a direct `/fix` creates at its start (Standalone Mode Minimum Contract §4a). This file is the one owner of the task for every route; it replaced the advisory post-fix lesson check. It runs before the verify, so the guard is reviewed and verified with the fix (`SYNC:verify-last-order`).

**Purpose:** a fixed bug belongs to a class that will strike again elsewhere unless something stops it. Ask why the class can happen at all, find the copies it already has, and guard the whole class with the strongest guard you can afford, so the next copy cannot be written, rather than telling people not to write it. The task ends in one prevention record that a checker validates; `/workflow-end` refuses to close a run whose `recurrence-guarded` gate has no valid record.

**Who runs it:**

| Route | Owner of the task |
| --- | --- |
| `workflow-bugfix` | its `bugfix-prevent` gate; the `bugfix-fix` step skips it |
| `workflow-review-changes` (`--fix-loop`) | its `prevent-recurrence` step, once, after `fix-findings`, when a fixed finding was a behavior defect; when every fixed finding was style, naming, documentation or coverage only, that step is skipped and the `fix --target=review` step writes the one-line `not-applicable` record itself (step 0), so the commit reminder clears |
| direct `/fix` (no flag or any `--target`) | the fix itself, as spine task §4a before the reviews |
| `/fix` nested under any other caller (a `/changes-review --fix-loop` fix step, an integration-test or E2E fix loop, another workflow's fix step) | the fix itself, before it returns, so the caller's review of that round covers the guard |

0. **Is there a code defect to guard?** A fix that repaired a style, naming, documentation or coverage-only finding, or changed no behavior, writes a one-line `not-applicable` record with its `reason` (step 6), reports `Prevention: not applicable — <reason>` and stops. That record clears the commit reminder, but it never satisfies the `recurrence-guarded` gate of a workflow, so it cannot stand in for a guard after a real defect. A cause the investigation traced to the environment (toolchain, configuration on one machine, a resource limit) is recorded as `not-a-code-defect` with that evidence; the environment is fixed in the environment.
1. **Name the bug class** from the `Bug class:` line of the `investigate --mode=debug` hand-off, with the root-cause `file:line`. The class names the kind of mistake, apart from its business subject, from a closed vocabulary (`node .claude/hooks/lib/prevention-record.cjs classes`): `state-transition`, `concurrency-ordering`, `idempotency-replay`, `missing-value`, `boundary`, `error-handling`, `contract-drift`, `duplicated-rule`, `data-integrity`, `security`, `performance`, `test-reliability`, `configuration`, `build-tooling`; `other` with a short `classNote` only when none fits. A hand-off without the line: classify it here from the trace.
2. **Ask why this class can happen at all.** Not the trigger of this instance, but what in the design lets anyone write this bug: a state field any caller may set, an API that needs expert nuance to call safely, a lookup that can return nothing with no type saying so, one rule kept in two places, a retry with no idempotency key. This answer points at the guard.
3. **Sweep sibling instances.** Search the project for the same pattern, not the same business subject: cite the query, the count and each `file:line`. Report them; never fix them silently outside this change. A copy that a comment justifies is still a sibling, and a workaround found on the way is reported, never copied. Each sibling becomes a follow-up the user decides on, or an entry in the frozen baseline of the guard below.
4. **Pick the strongest affordable guard, structure-first** (the tiers of `/learn`'s Prevention Depth Assessment): make the class impossible by design (a type, a structure, or a wrapper that restricts an API needing expert nuance), else a lint rule or architecture test whose message names the fix and whose frozen baseline holds the swept siblings (green when it lands, the next copy fails, the baseline only shrinks), else a test, else a hook; a prose lesson through `/learn` comes last. Note why each stronger tier does not fit; the cost should be proportional to how often the class recurs. The test tier per class: `state-transition` → a stateful property test that runs random command sequences against a simple model and checks the spec's transition invariants after every step (`integration-test/references/integration-test-patterns.md`, Pattern 9, stateful variant); `concurrency-ordering` → a test that forces the losing interleaving; `idempotency-replay` → a test that delivers the same request twice and asserts one effect.
5. **Implement it, or record why not.** A guard that fits this change (a test, a wrapper at the owning layer, a narrow rule with its baseline) is written now, in the same change, so the review and the verify cover it. A guard bigger than the fix, a new tool or library (installing one always asks first), or a prose lesson needs the user: ask through the host question tool, the chosen tier first as `(Recommended)`: `Add the <tier> guard`, `Save with /learn` or `Skip` when the tier is structural; `Save with /learn` or `Skip` when the walk ended at prose. A structural pick that is bigger than this fix is planned as its own reviewed change (`/plan`), never folded silently into this fix; record it as `no-guard` whose owner is that planned change. On `Save with /learn`, invoke `/learn` with the generalized lesson, its bug class, the evidence and the tier walk already done (so it does not offer a declined guard again); `/learn` chooses the carrier, runs its own confirmation and saves. `Skip` records `no-guard` with the reason "declined by the user". A lesson candidate is kept only when all three hold:
    - **Generic** — it names no business rule (a business rule belongs in the spec and its tests, not in a lesson).
    - **Likely to recur** — the sweep, sibling code or past fixes show the same pattern, or the class is common in this stack; cite what you searched.
    - **Not already covered** — no lint rule, type check, test or hook catches it, and the project's lessons and reference docs do not already say it (search them).
6. **Write the prevention record** as one JSON file under `tmp/prevention/records/` (for example `tmp/prevention/records/<YYMMDD-HHmm>-<slug>.json`; `node .claude/hooks/lib/prevention-record.cjs template` prints the skeleton): `schema` 1, `bugClass`, `rootCause`, `why`, `outcome`, and per outcome:
    - `guarded`: `siblings` (`query`, `count`, `locations`) and `guard` (`tier`, `path` — the repository-relative file that holds the guard, which must exist and not be git-ignored);
    - `no-guard`: `siblings`, `reason` and `owner` (the person, team, ticket or planned change that decides on the class later) — a trivial one-line fix may record this in one line;
    - `not-a-code-defect`: `evidence`;
    - `not-applicable`: `reason` only (no class, sweep or guard), for a fix that repaired no behavior defect (step 0).
    The record names files and classes only; never a secret, a token or an environment value (the checker rejects values shaped like one).
7. **Check it** with `node .claude/hooks/lib/prevention-record.cjs check --file=<record path>` and read its JSON: `VALID` closes the task; `INVALID` lists each field, the problem and the fix — correct the record (or add the missing guard) and check again. Never edit a record to pass without the guard or the reason it describes.
8. **Report** in the fix or workflow report: `Prevention: <class> — <count> siblings (<query>) — guarded by <tier> at <path>`, `— no-guard (<reason>; owner <owner>)`, `— not a code defect (<evidence>)`, or `Prevention: not applicable — <reason>`; plus the record path for `/workflow-end`. When `commit.bugClassTrailer` is `true`, the class reaches the commit as `Bug-Class: <class>` (`commit/references/trailers.md`).

**Worth guarding:** shared mutable fixtures make tests flaky → a fixture factory or a test-isolation lint rule; an unchecked lookup crashes → a lookup wrapper that returns an explicit "missing" result; one query per row slows a page → an architecture test that forbids data access inside a loop body; an order can be shipped twice → a stateful property test over the order lifecycle. **Not worth a lesson:** a business rule the code violated, a one-off typo, a rule a check already enforces — those still get a record (`no-guard` with that reason, or the guard that already exists).

**Limits:** never fix a sibling silently, never save a lesson or install a tool without the user's answer, and never weaken a check to make a guard land. A sub-agent or headless run cannot ask: it writes the guard only when it fits the change without a question, otherwise records `no-guard` with the caller as owner and returns the candidate to its caller, which asks. This task covers the defect's class; the Lesson Extraction Gate still covers the assistant's own reasoning mistakes — when both find a lesson, ask about them in one question.
