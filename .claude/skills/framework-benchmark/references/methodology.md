# Comparison and assessment method

Read before designing a campaign or interpreting its result. The hypothesis is that the complete framework improves task outcomes enough to earn its overhead; raw-equivalent and raw-better are equally valid possibilities.

## Chosen experiment

Use a frozen paired single-attempt design: same brief, application bytes, backend, installed CLI version, requested solver model and limits; fresh environments; one declared full-framework intervention. Docker additionally pins the execution image. Keep requested and observed model identities separate, with unknown observations explicit. Alternate the first arm by a recorded seed parity. The seed controls order, not model sampling determinism. Repeat without retrying a weak answer. Report individual outcomes and paired differences; do not select the best attempt.

Greenfield treatment starts through the greenfield initialization workflow and completes the brief. Brownfield bootstrap creates project config/reference docs through project initialization before task work. A configured consumer uses its own committed setup. Raw excludes those setup artifacts and all known agent instruction surfaces, while ordinary application documentation stays common. Raw also runs with no skills at all, including skills built into the assistant CLI, so the treatment is everything the framework adds plus whatever built-in skills the framework arm's assistant exposes; the assistant cannot disable only its built-ins while keeping installed skills. This is package-level attribution, including setup and workflow overhead.

Freeze checks before seeing answers and withhold them from solver inputs. Use task acceptance plus regression checks, calibrated on the initial state; a feature's acceptance may initially fail, while a refactor's preservation check must initially pass. Candidate-authored tests cannot replace frozen checks. A command-level result is not an inferred count of all individual assertions. Native worktrees separate supplied source/history and fresh attempt context; they do not contain malicious code or prove outside holdouts are unreadable. Native campaigns require trusted tasks/code/checks and disclose normal CLI permission limits; Docker retains its stronger container boundary.

Use the same frozen neutral role/skill toolkit for anonymous reviewers of both arms, with no solver transcript, project-setup context or arm label. New native preparations use discovery followed by fresh independent claim validation, with at most a third fresh pass for new consequential claims. Retain every allegation and its confirmed/rejected/unresolved disposition, deduplicate confirmed causes and count unvalidated claims separately. Reviewers may write public reports and run bounded checks but cannot fix candidates or advise solvers. Missing capability, identity, integrity or adjudication evidence stays ungraded.

Assess eight equal-weight dimensions from 0–4, requiring existing relative artifact path/line evidence. Plans, decisions and review artifacts use deliverable-appropriate meanings. A wholly empty result receives zero dimensions with an explicit empty-artifact receipt; it cannot cite invented files. Keep scores separate from objective task success. Qualify known healthy and defective reviewer controls before solver answers, withholding expected verdicts and retaining missed defects/false positives. Read [complex-corpus.md](complex-corpus.md) for task/template and calibration exit conditions. Anonymous style can still reveal the production process, and same-family reviewers may share blind spots; model judgments remain proxies pending appropriate human/domain-expert calibration.

Passively retain a bounded public-action record and use a fresh read-only session to synthesize each execution journey after the solver ends. This observer can see the production process; it is separate from the anonymous outcome assessor. Keep chronology, declared versus observed decisions, context reads, skill receipts versus workflow completion, tests, failures, recovery and unknown helper/hook activity explicit. Require real trace citations and observed/inferred/unknown distinctions; citation existence is not semantic truth or assessor calibration. A narrative is qualitative diagnostic evidence, not a causal explanation or a replacement for outcomes. Compare the raw-better and framework-better explanations equally, retain unfavorable stories and measure observer overhead separately.

Treat known-runtime timeouts, task failures and treatment non-engagement as failed attempts. Infrastructure/identity/grading failures are invalid evidence and stay visible. Show complete and missing measurement coverage, including cache tokens, costs and evaluator overhead. Native subscription charges remain unknown when not reported; an API-equivalent estimate is separate from billing and any loop allowance. Do not infer internal/subagent usage absent from telemetry. Retain candidate/setup work, observations and cleanup outcomes before removing only verified experiment-owned temporary work.

## Primary-source basis and alternatives

- [SkillsBench](https://arxiv.org/abs/2602.12670) compares skill conditions with deterministic verifiers and reports variable benefits. [SWE-Skills-Bench](https://arxiv.org/abs/2603.15401) uses pinned repositories and paired requirement-driven checks and reports limited average gains. Together they support measuring both benefits and regressions, not presuming an effect here.
- [SWE-bench evaluation](https://www.swebench.com/SWE-bench/guides/evaluation/) and [Inspect sandboxing](https://inspect.aisi.org.uk/sandboxing.html) support reproducible isolated execution and separating infrastructure failures from task results. [Harbor task format](https://docs.harborframework.com/tasks/overview) separates task/environment/verifier artifacts.
- [Anthropic's agent-evaluation guidance](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) describes combining outcome graders with model/human assessment and repeated trials. The [MT-Bench judge study](https://arxiv.org/abs/2306.05685) documents position, verbosity and self-enhancement bias; a rubric score is not objective correctness.
- [SWE-bench Verified](https://www.swebench.com/verified) uses human review of task clarity, test correctness and solvability. That supports pre-answer corpus/check qualification here; it does not certify this locally authored corpus. Our bounded fresh claim-validation chain is an engineering choice to challenge allegations, not a published guarantee of reviewer accuracy.
- [NVIDIA SkillEvaluator](https://github.com/NVIDIA/SkillEvaluator), Harbor and Inspect are alternatives for broader evaluation programs. This framework uses a smaller built-in Node orchestrator with native account-backed CLI adapters and an optional container adapter to remain copyable with its existing tooling. The tradeoff is adapter maintenance and limited runtime/platform proof. Revisit integration when remote scale or additional backends justify it.

Confidence is high in the paired/isolation/outcome-check principles across these sources; the local implementation choice is an engineering judgment, not a measured result those sources establish. This is a scoped primary-source survey, not an exhaustive census of community practices.

## Community practice re-verified (2026-10-28)

Each row is a design choice in this skill, the practice it follows, and the primary source checked.

| Practice | Source | How this skill applies it |
|---|---|---|
| Measure skills with paired with/without runs on pinned repositories and execution tests; expect many skills to show no gain and large token overhead | [SWE-Skills-Bench](https://arxiv.org/abs/2603.15401) (39 of 49 skills no pass-rate gain; token overhead up to +451% at unchanged pass rates) | Raw versus full-framework pairs on frozen bases with frozen checks; tokens and time reported beside outcomes |
| Compare conditions on the same tasks with deterministic verifiers; curated and self-generated skills differ | [SkillsBench](https://arxiv.org/abs/2602.12670) (no-skills, curated and self-generated conditions) | Raw is the no-skills condition; `compare` breaks results down by single-skill and workflow treatments |
| Inference on paired per-item differences, with error bars clustered by related items | [Adding Error Bars to Evals](https://arxiv.org/abs/2411.00640) (clustered errors can exceed naive ones several times) | One row per task with repeats pooled as one cluster; exact sign test plus a paired 95% t interval over tasks |
| Sandboxed tasks with an environment, instruction and verifier tests judged on the final state (verifier details from task documentation, not the landing page) | [Harbor](https://harborframework.com), from the Terminal-Bench makers | Frozen acceptance and regression checks on fresh candidate copies; baseline calibration and corpus qualification before solvers |
| Combine code, model and human graders; calibrate model graders against humans; run several trials and choose pass@k or pass^k by whether one success or consistency matters; read the transcripts | [Anthropic: Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) (2026-01-09) | Frozen checks plus a two-pass skilled reviewer with claim validation, seeded healthy/defective controls and a separate journey observer; 1–20 repeats per pair; human calibration remains a stated limit |
| LLM judges show position, verbosity and self-preference bias, worse on hard code tasks | [MT-Bench judge study](https://arxiv.org/abs/2306.05685) and later code-judge studies | Pointwise anonymous grading, citations required, scores never override checks; same-family judges are disclosed as symmetric bias, and a different judge model can be frozen in the runtime |

A task that both arms fail completely is first examined as a possibly broken or ambiguous check, as the agent-eval guidance advises; a post-hoc sensitivity re-check is reported separately and never replaces the frozen result.

## Conclusions the report supports

A case report supports scoped observations about its exact task, inputs, requested/runtime model identities and framework version. Multiple attempts on one case remain correlated. It supplies descriptive deltas, not population confidence intervals or a universal superiority claim. Use several independent realistic tasks, task-level aggregation, held-out variants and calibrated reviewers before broader claims. The `compare` command implements the task-level step: one row per task (repeats pooled, never counted as extra tasks), framework win/raw win/tie per task on success and on quality (quality gaps under 5/100 are ties, because one dimension point is 3.125), and an exact two-sided sign test over non-tied tasks. It states a direction only with at least six decisive tasks and p < 0.05, the same bar for either arm; fewer is insufficient evidence, because even a clean five-task sweep has p = 0.0625. The sign test was chosen over a paired t-test or bootstrap interval because task-level effects are few, ordinal and not normally distributed; it ignores effect size, which the per-task deltas and median time/token ratios report alongside it. Changing a prompt, check, framework package, setup, model or environment invalidates comparisons with earlier identities.

Bias check: the benefit premise and raw-better opposite use the same evidence bar; neutral or negative trials and credible new evidence can reverse the recommendation.
