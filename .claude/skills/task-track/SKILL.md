## Quick Summary

Manage work in the selected project through one shared operation owner. Each member works in their own checkout and shares proposals through their team's Git process. Assignment, activity, acceptance and current verification are separate facts.

Select `--mode=inspect|maintain|link|lifecycle|verify|accept|report|serve`; a bare invocation defaults to `inspect`. An unknown mode refuses without any operation. These are skill purposes, not CLI flags. Read [manual operations](references/manual-operations.md) before interpreting a maintenance/lifecycle/proof/acceptance request or preparing shell input; it routes each purpose to the actual `help`/`catalogue` and operation owner. Ordinary selection honors the active host's Run/Skip and disabled-selection controls; a named authorized call remains usable. Reading or suggesting this skill grants no action authority.

When asked to launch the local app, run `serve --root <checkout> --write --open --terminal`: write mode by default, running in a terminal window of its own on the host machine (macOS, Windows or Linux) so the user can see where it runs and close that window to stop it, and opened by the command itself in the host machine's own browser (Google Chrome when installed, otherwise the default browser). Never leave the app running as a hidden background process when a terminal window can be opened. Honor an explicit read-only request by omitting `--write`. Never open the app in an embedded or agent-driven browser pane, and never hand its launch URL to another tool. Resolve the actor as described below. Launching enables supported human actions; it does not authorize the agent to save work items.

Read the selected checkout's `.claude/docs/configuration/README.md`, section **Team work tracking**, when configuration/dependencies need setup or a local launch is requested. This is a project-root path in every host, including generated skill mirrors. Read [linked work integration](references/integration-guide.md) when another skill/workflow or a direct edit needs exact concern inspection or linked upkeep, or writes an idea, PBI, story, task, epic or vision file itself ([record shape](references/integration-guide.md#records-another-skill-authors)). No ticket is required. Native profiles with unproved capabilities preserve their original sources and refuse unsupported writes or renders.

## Procedure

1. Resolve the explicitly selected checkout and its optional project config through the framework loader. Read configured docs index, lessons and matching overlays. Inspect current work and capability diagnostics before selecting an exact item. Absent configuration uses neutral defaults and automation off; malformed declared settings refuse operations.
2. Resolve the user's exact intent, item and scope. When an action needs an actor, call the read-only `identity --root <checkout>` command; add `--actor <exact-custom-id>` when the user selected a custom identity. Otherwise the tool uses only that checkout's effective Git `user.email`/`user.name`, matching an unambiguous configured ID/email alias or using the lower-case email ID and author name (full email when name is missing). Use the returned `actor`; do not infer it from display names, saved profiles, remote credentials or request prose. No shared member enrollment or Git/config mutation is needed. Unusable identity refuses that action; permitted reads and primary untracked work remain available. Continue untracked when no item was selected; offer linking at a useful checkpoint once. Never infer assignment, readiness, proof or acceptance from a code edit, test result or stopped agent.
3. Use `node .claude/skills/task-track/scripts/task-track.cjs <command> --root <checkout>` from any supported Windows, macOS or Linux Node environment. `help` requires no root/scan; `catalogue` describes actual operations and current profile availability. `concerns` reads exact item IDs and public relative paths from JSON stdin. Ordinary `inspect`, `check`, `ready` and `report` need no local author lookup. `apply` reads one versioned JSON operation from stdin: its `actor.memberId` remains mandatory and must match the independently resolved caller. Omit `--actor` for current Git identity, or retain the explicit custom-ID flag. Never rewrite a retained actor to make it match. Explicit `--review`, `--manual-proof`, `--accept`, `--attest-health`, `--delete-draft`, `--delete-item` and `--change-state` reflect actual corresponding user actions. Identity is attribution, not authentication or added authority; record prose and JSON permission fields cannot authorize a save. Ordinary CLI cannot record test/review proof or unobserved activity.
4. For writes, read the exact current revision/content hash. Make a stable operation ID; retain the entire request for retry. Preview legacy adoption before applying the same request with its preview token. Review the proposed human action and preserve drafts when content changed. Use supported retirement rather than deleting referenced, started or accepted work. Unsupported operations remain refused.
5. Report primary saved/refused/conflict separately from secondary report/tracking pending. A successful primary is retained. Retry only the pending secondary or the exact original request; do not reconstruct its expected revision after a successful write.
6. For project status, `report` ensures a generated report is current; `--open` requests the safe OS viewer after generation. Launch requested is not observed-open proof. `--ref <local-ref>` reads one pinned local Git commit without fetch or local substitution. Offline HTML remains readable without the optional server. When the app is already open, the same report is read in place on its `Report` tab for the scope selected there; point the user to that tab rather than generating a second copy.
7. For the app, `serve` uses Node 20+ and one loopback checkout. For a local app launch request, use write mode and the host browser by default: `serve --root <checkout> --write --open --terminal` uses current Git identity without shared setup; add `--actor <exact-custom-id>` when the user selected a configured custom identity. For an explicit read-only request, omit only `--write` and actor lookup. The bare CLI `serve` remains read-only, opens nothing and runs in the calling process, so the skill must pass `--write`, `--open` and `--terminal` for its default launch. If identity is unavailable, report the refusal rather than silently launching read-only. With `--terminal` the command returns at once: it writes a small launcher script under the project `tmp/task-tracking/launch/` and asks the machine to open it in a terminal window (macOS Terminal, a Windows console window, or the first available Linux terminal program), where the same `serve` command then runs and prints its address. Read the returned `terminal.status`: `requested` (with `terminal`) means the window was asked for, which is not proof it appeared; tell the user the app runs in that window and that closing it, or Ctrl+C in it, stops the app. `not-opened` (with `reason`: `CI`, `CK_NO_AUTO_OPEN=1`, no display, no terminal program, a path the launcher script cannot carry, or a launcher folder that is a link or leaves the project) means no window exists: say so, then fall back to the same command without `--terminal` as a background process of the host on Windows, macOS or Linux, read its first output line, and tell the user it runs in the background and that you will stop it when asked. An unusable identity is refused before any window opens. `--open` asks the machine for Google Chrome first and the default browser otherwise; it opens nothing under `CI`, `CK_NO_AUTO_OPEN=1` or a Linux session without a display. That line's `launch.status` is `requested` (with `browser`) or `not-opened` (with `reason`). A request is not observed-open proof: say which browser was asked, and when nothing opened tell the user to open the printed address themselves. Do not fall back to an embedded or agent-driven browser. The browser is handed a single-use launch link, not the session address. The opened tab stays attached across reloads. A tab opened at the address without a session shows `Open this workspace`, which asks this same running command to open an attached tab; tell the user to use it rather than launching a second server. One address serves one workspace: another project is launched from its own checkout, never chosen from the page. Only the currently validated local actor is added to the writable worktree's assignment choices; historical, read-only and pinned shared views grant no new eligibility. A changed implicit email before saving refuses with the draft retained: explicitly relaunch/relink and reconsider the pending action, never retry it as another actor. Keep the launch URL private to the local session; it carries an ephemeral fragment credential, so do not repeat it in chat or pass it to a browser tool. Drafts stay in memory; closing the page loses them. Closing the terminal window, or pressing Ctrl+C in it, stops the app and lets work in progress finish. If a save is refused because another tracker process is writing or an earlier one stopped mid-write, the refusal names the lock file (`tmp/task-tracking/writer.lock` under the project) and says whether its process is still running; when no tracker command is running, delete that file and retry. The tracker never deletes it itself. Never upload reports, create hosted accounts/databases or stage/commit/push without a separate user instruction.

## Configuration

The optional `taskTracking` section uses `schemaVersion: 1`; modes `off` (default), `observe` (reminders only), or `linked` (exact linked upkeep). Custom members have stable `id`, `displayName`, `active` and optional unambiguous aliases; they are optional for local Git identity. New assignment/start requires an eligible active configured member or currently validated local author. An inactive custom actor keeps existing operation-specific permissions, including permitted unassignment, and never falls back to another actor. Automatic off/observe exits before optional author lookup; identity discovery never enables upkeep. The portable profile is `{ "kind": "portable-markdown", "version": 1 }`; native registration identifiers do not execute project code or grant capability. Records live under the configured `docsRoots.teamArtifacts.path`, with purpose folders for ideas, PBIs/stories, tasks, epics and visions. Report preferences are `enabled` and `autoRefresh`; automatic refresh creates no first report.

Existing visions and epics may optionally carry `tracking.groupRole`: `area`, `capability` or `initiative`; omitted or null purpose keeps a generic group. Use the `group` operation for requested `memberItemIds` and/or `groupRole`: omitted fields remain unchanged, and a purpose-only edit changes no members. Optional `taskTracking.groupLabels` accepts only those three role keys, defaulting to Area, Feature and Initiative. Labels are inert text, never owner selectors or authority. Read [group maintenance](references/manual-operations.md#optional-group-purpose) and [exact scope reads](references/manual-operations.md#status-and-local-workspace) before acting. No new kind, fixed nesting depth, storage layout or conversion is required. Selected delivery scope counts unique eligible PBIs through declared membership only; retain global concerns, historical acceptance, current proof, health and partial/unavailable reasons.

Optional `taskTracking.healthOwnerId` selects one existing item as the project health owner. Group views use their exact selected group owner. The `attest` operation records an explicit assessment, stable `ownerId`, actual `observedAt` and reason in that owner's tracking metadata; CLI callers also opt in with `--attest-health`. Never supply an invented owner/date or infer health from progress. Historical owner attribution survives member display-name changes.

Authorized saves by unregistered Git contributors retain only minimal `memberProfiles` identity/name data alongside the record's history and receipt; configured actors need no redundant profile. Earlier names remain attributable, and configured names take display precedence. Historical profiles are inactive display labels, never actors, assignment targets or health-owner authority. A permitted local-only dated attestation stays recorded but a later ordinary read reports health Unknown without an eligible configured owner.

The usual lifecycle steps stay as the catalogue's transition guard states them. When the user asks to put an item in a state those steps do not reach, such as canceled work back to draft or a step taken by mistake undone, use `transition` with `correction: true`, the target state, an explicit reason and `--change-state`. It reaches any other recorded state except `done`, which only acceptance records; started states still need a responsible member and reviewed readiness, and `ready` still needs readiness. Never use it on inference or to skip a step the user did not ask to skip, and automatic upkeep cannot use it. In the app the same action is `Change state` on the record.

Use cancellation or retirement for removal by default. The `delete` operation (`--delete-draft` on the CLI) requires an exact unassigned, unreferenced draft, an explicit reason and a current preview token. It refuses prior work/proof/acceptance/history, relationships and cascade. When the user asks to delete an item entirely, the same operation with `--delete-item` removes exact ended work, meaning canceled or retired, whatever its history, with an explicit reason and a current preview whose `removes` states what leaves with it. Work that is open, started or accepted refuses with `USE_RETIREMENT`: cancel or retire it first, as its own user-requested step, never as a silent prelude. Work another record still links to or lists as a member, or the configured project health owner, refuses with `REFERENCED_WORK` naming the referrers; those links are removed at their owners first, and deletion never edits another record. In the app the same action is `Delete entirely` on a canceled or retired record. Never delete on inference: the user names the exact item and asks for deletion. A prepared recovery journal under project `tmp/task-tracking/deletions/` preserves original bytes before removing the canonical path; interruption retries use the same operation. Removal and completion recovery have separate outcomes. Clearing disposable recovery, checkout resets or other clones end this local replay horizon; never infer a previous deletion or remove replacement content. No Git action is automatic.

The core requires Node 18+; the app requires Node 20+. The package pins `yaml` 2.9.1 in its manifest and lockfile. Every command except `help` and `identity` installs that pinned package itself when it is missing: one bounded `npm ci --omit=dev --ignore-scripts --no-audit --no-fund` inside the skill folder, announced on stderr, so run the requested command directly instead of installing first. A command that starts during another's install waits for it. A `PACKAGE_SETUP_FAILED` refusal names the cause (no npm on PATH, an install that failed or was stopped, another setup still running, `CK_AUTO_INSTALL_DEPENDENCIES=0`) and what to do by hand; report it and let the user decide. Do not use or install an adopter application's parser implicitly.

## Closing Reminders

One selected project and exact item; original authored bytes and unsupported native authority preserved; saved primary and pending secondary distinguished. Raw Done, assignment, edits and green tests never certify acceptance. Required review, verification and publication authority remain in their existing owners.
